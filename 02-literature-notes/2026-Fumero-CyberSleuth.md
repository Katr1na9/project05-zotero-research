# CyberSleuth: Autonomous Blue-Team LLM Agent for Web Attack Forensics

## 1. 基本信息

- 英文题名：CyberSleuth: Autonomous Blue-Team LLM Agent for Web Attack Forensics
- 中文译名：CyberSleuth：面向 Web 攻击取证的自主蓝队大模型智能体
- 作者：Stefano Fumero; Kai Huang; Matteo Boffa; Danilo Giordano; Marco Mellia; Dario Rossi
- 年份：2026（arXiv v2，2026-03-05）
- Venue：arXiv preprint
- DOI / arXiv / URL：https://arxiv.org/abs/2508.20643
- Zotero key：EEMDSX3E（PDF attachment：CIE3LXGG）
- 阅读日期：2026-07-13
- 阅读优先级：必读
- 所属主题：LLM-Agent / PCAP Forensics / Attack Investigation / Evidence Correlation

## 2. 一句话总结

CyberSleuth 系统比较三种 LLM 取证智能体架构，让智能体从 PCAP 中识别目标服务、精确 CVE 和攻击是否成功，并生成取证报告。其主要结论是：专门的流摘要器加简单串行编排比单智能体或嵌套智能体更可靠，但系统仍是流量单线、报告级证据组织，尚未构建可持久查询的事件证据图，也未推断 ATT&CK 阶段或攻击意图。

## 3. 研究问题

- 核心问题：LLM 智能体能否直接使用原始 PCAP 和取证工具，自动完成事后 Web 攻击调查？怎样的记忆、工具和多智能体编排更有效？
- 任务输出：目标服务、被利用的具体 CVE、攻击成功与否，以及结构化取证报告。
- 重要性：人工网络取证耗时且依赖协议与漏洞知识；LLM 虽有推理能力，却容易在长上下文、工具调用和多智能体协调中失焦。
- 与本课题关系：直接覆盖“流量侧观测 -> LLM 取证推理”；没有覆盖“流量 + 日志双线 -> 统一事件证据图 -> 攻击链/意图候选”。

## 4. 核心贡献

1. 系统贡献：实现三种可比较架构，即 Single Agent、Tshark Expert Agent（TEA）和 Flow Reporter Agent（FRA）。
2. 方法贡献：引入 MemGPT 风格的短期 FIFO、外部长时向量记忆和聚焦 Web 检索；FRA 使用专门流摘要器先提取证据，再由主智能体推理。
3. 数据贡献：基于 CFAbench 的 20 个 Web 攻击事件增加 10 个 2025 年新漏洞事件，并补充 10 条良性浏览轨迹。
4. 实验贡献：比较 3 种架构和 6 个 LLM 后端，并用 25 名专家评价报告；另在 10 个恶意软件流量事件上验证迁移性。
5. 经验贡献：简单的串行专门化优于嵌套协调；高自由度工具调用会造成失焦，而不可回看原始数据的串行流程又限制自纠错。

## 5. 方法框架

### 输入

- Web 攻击：已过滤出攻击相关通信的 PCAP，假设 WAF/TLS 终止点可以提供明文流量。
- 恶意软件场景：感染主机的 PCAP，包含背景流量及 C2、载荷下载或数据外传活动。
- 外部知识：Google Custom Search 返回的网页摘要，用于验证服务、攻击类型和候选 CVE。
- 需要注意：正式实验中 PCAP 是唯一智能体输入；应用日志仅用于离线检查其诊断价值，没有进入主方法。

### 输出

- 目标服务及版本线索；
- 对应 CVE；
- 攻击成功/失败判断；
- 包含流量证据和外部检索依据的取证报告；
- 恶意软件迁移实验额外输出受害者信息和 IOC。

### 关键模块

| 模块 | 作用 | 可借鉴点 |
|---|---|---|
| Flow Summariser | 按 TCP/UDP 流重组 payload，输出服务、相关事件、可疑活动和成功证据 | 可作为流量线的证据抽取器，但输出应进一步变成稳定的证据节点 |
| Focused Web Search | 在观察 PCAP 后检索服务 + 攻击类型，汇总前 10 个结果 | 外部知识只能验证候选，不能替代事件内证据 |
| FIFO + Vector Memory | 保存近期动作和 Top-10 语义相关历史经验 | 可用于长调查，但检索命中不等于证据可追溯 |
| Main Agent | 融合流摘要和网页知识，判断 CVE/攻击结果并写报告 | 适合作为图谱之上的推理与叙事层 |

### 方法流程

```text
PCAP
  -> packet/flow preprocessing
  -> Flow Summariser（逐流 tshark 重组与结构化摘要）
  -> 主智能体 + 短/长时记忆
  -> 聚焦 Web 检索验证候选 CVE
  -> 服务、CVE、成功性与取证报告
```

三种架构的差异：

- SA：主智能体从全包摘要中挑包，再调用 PCAP Reader。
- TEA：主智能体从流列表出发，动态指挥 tshark 子智能体；精细但协调失败频繁。
- FRA：流摘要器独立完成系统性检查，主智能体只消费一次结构化摘要；可靠且便宜，但不能回看原始证据。

## 6. 数据集与实验

- Web 设计集：20 个受控事件，14 次成功、6 次失败；数据量从十余包到近万包。
- 2025 独立测试集：5 个新披露漏洞，每个部署易受攻击与已修补版本，共 10 个事件。
- 良性集：10 条普通浏览轨迹，其中 2 条含人为输错密码。
- 恶意软件迁移集：10 条 Malware Traffic Analysis 公开 PCAP，覆盖 Loader、NetSupport RAT、Koi Stealer、WarmCookie、STRRAT、Emotet、IcedID、Cobalt Strike 等。
- 指标：Service accuracy、CVE accuracy、Attack-success Accuracy/F1/MCC、步骤数、输入/输出 token、成本；报告由 25 名专家按完整性、实用性和逻辑连贯性评分。
- 架构结果（GPT-4o）：FRA 的 Service/CVE/Success Accuracy 分别为 0.67/0.45/0.62，MCC 0.45，优于 SA 和 TEA；平均成本约 10.78 美元/20 个设计事件。
- 后端比较：GPT-5 的 Service/CVE 为 0.80/0.68；o3 的成功判断 MCC 为 0.65；DeepSeek R1、Kimi K2 在多项指标接近闭源模型且成本更低。
- 2025 测试：GPT-5 与 o3 的攻击成功判断准确率均为 0.90；论文概括 CyberSleuth 在未知 2025 事件上达到最高 80% 的整体关键任务表现。
- 良性轨迹：未错误报告明确攻击；两次重复快速登录失败被提示为潜在暴力破解迹象。
- 报告评价：完整性、实用性、逻辑连贯性平均约为 4.33、4.23、4.31/5。
- 迁移结果：10 个感染事件中 9 个正确提取受害者信息，并能提取主要 IOC；论文未对完整攻击链重构给出结构化指标。

## 7. 关键知识点

### 概念

- 取证任务需要把“发现线索、外部知识验证、成功性判断”分开评测，单一最终准确率会掩盖错误传播。
- 简单串行编排可以降低多智能体协调损耗，但会牺牲反复回到原始证据自我修正的能力。
- 流摘要是上下文压缩机制，不自动等价于可核验的证据链；摘要中遗漏的传输层信号会永久丢失。
- Web 检索结果包含正确 CVE 并不保证 LLM 会选对，检索与推理应分别评价。

### 技术路线

- payload 超长时采用平方根分配：各流按 `sqrt(tokens_i)` 分配预算，并各取流首尾一半。
- 对 TLS 加密流直接跳过 payload 摘要，依赖监测点能解密关键会话的强假设。
- 搜索查询避免直接写候选 CVE 编号，要求先包含已观察到的服务和攻击类型，以降低先验臆测。

### 术语翻译

| 英文 | 建议译法 | 备注 |
|---|---|---|
| post-mortem forensics | 事后取证 / 事后调查 | 事件发生后的证据重构 |
| flow summariser | 流摘要器 | 不是攻击链重构器 |
| attack success evaluation | 攻击成功性判断 | 不等同于告警分类 |
| coordination gap | 协调鸿沟 | 主智能体与工具智能体间任务传递失真 |
| context traceback | 上下文证据回溯 | 本文没有实现严格贡献度追踪 |

## 8. 优点

- 直接从 PCAP 调用 tshark，而非仅消费人工预处理的文本描述。
- 系统比较架构、模型、成本和失败模式，避免只展示单个成功案例。
- 新增 2025 漏洞测试，部分缓解模型训练语料记忆带来的泄漏。
- 明确报告工具协调、长流量失焦、检索选错和传输层证据遗漏等失败机制。

## 9. 局限

- 受控容器/实验环境与真实企业网差距明显；Web 场景预先过滤无关流量，降低了证据发现难度。
- 依赖明文或可解密流量；对加密流、扫描发现和多事件并发的支持不足。
- 日志没有进入智能体输入，因此不是 PCAP + log 双源融合方法。
- LangGraph 只描述智能体控制流；系统没有构建事件级证据图、时间因果边或可查询的跨源实体关系。
- FRA 不允许主智能体重新查询流摘要器或原始 PCAP，难以做假设驱动的迭代取证。
- 输出集中在服务、CVE 和成功性，未系统评价 ATT&CK 阶段、攻击链完整性、意图识别或行为体归因。
- 报告专家评价只覆盖 4 个已成功调查的事件，存在选择偏差；没有逐项验证每个自然语言声明是否由原始包支持。

## 10. 对我选题的启发

- 可以直接借鉴：流量侧专门解析器与 LLM 推理层解耦、分阶段指标、对近期漏洞做时间外测试。
- 可以改进：把一次性流摘要改为带 `pcap/frame/flow/timestamp/field` 锚点的事件证据节点；日志侧按同一事件本体构图。
- 可以作为 baseline：CyberSleuth/FRA 式“PCAP -> 摘要 -> LLM 报告”单线基线。
- 可以用于研究动机：单源摘要无法回看会漏掉传输层信号，动态工具智能体又会失焦，说明需要可查询且持久化的证据中间层。
- 可以用于实验设计：分别评价流量单线、日志单线、简单文本拼接、双线证据图融合，以及去掉证据回溯/冲突处理后的消融。

## 11. 可转化的研究问题

1. 事件证据图能否在保持 FRA 稳定性的同时，恢复 TEA 的按需回查能力？
2. 流量证据与主机/应用/蜜罐日志互补后，能否提高攻击阶段覆盖率与成功性判断，并降低错误 CVE/意图结论？
3. 如何要求每个 ATT&CK 阶段或意图候选回指最小原始证据集合，并在两侧证据冲突时输出不确定性或拒答？
4. 五类网络环境/协议条件下，哪些证据锚点能保持不变，哪些需要协议特定解析器？

## 13. 论文写作可引用句式

- PCAP 取证智能体的主要困难不仅是模型知识不足，还包括长上下文压缩、工具调用可靠性和多智能体协调造成的证据遗漏。
- 专门化的串行证据抽取可以提升调查稳定性，但若中间摘要不可查询或不保留原始锚点，会限制后续的假设修正与证据复核。
- 检索命中正确漏洞并不等价于得到正确结论，安全调查应分别评价证据检索、候选选择与结论支撑关系。

## 14. 我的批注与疑问

- 这篇论文证明“PCAP -> LLM 调查”已经有较强直接工作，因此不能再把简单 PCAP 摘要加 LLM 报告作为创新点。
- 论文声称重构攻击时间线，但主要量化输出仍是服务/CVE/成功性；时间线和多阶段攻击链没有独立结构化评测。
- 应进一步检查其开源 benchmark 是否包含可与 Project03 PCAP/HFish 日志配对的事件字段。
- 我们需要避免用 Project03 的 `Predicted_Class`、`True_Attack` 或 `Technique` 作为推理输入，否则会发生标签泄漏。
